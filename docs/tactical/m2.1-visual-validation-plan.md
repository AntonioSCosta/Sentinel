# M2.1 — Plano de validação da representação C na arena M1.2

**Estado:** proposta. Nada foi integrado, alterado ou medido em hardware real.
**Âmbito:** uma cópia isolada do protótipo tático M1.2 que desenha os soldados com M1.2 ou com C,
mantendo tudo o resto igual. **Fora do âmbito:** IA, simulação, equilíbrio, mapa estratégico, campanha,
gravações, `index.html` e a versão jogável actual. A opção C só entra na versão jogável depois de nova
aprovação do maintainer.

## 1. Pergunta

C melhora a leitura das tropas nas condições reais do jogo — terreno, floresta, oclusão, câmara e
interface — sem custo de renderização incompatível com PC e browser, e pode ser desligada por
configuração? Em caso negativo, quanto do valor de C sobrevive apenas com os componentes baratos de A?

## 2. Experiência isolada

### 2.1 Ficheiros propostos

| Ficheiro | Papel |
| --- | --- |
| `tactical-m21.html` | Cópia de `tactical-proto.html`, com um bloco de configuração no cabeçalho (renderer, formação, stress, seed) e um selo com o modo activo |
| `src/tactical/m21/main.js` | Cópia congelada de `proto/main.js`; muda **apenas** o import da vista para o facade. Um comentário regista o SHA-256 do original |
| `src/tactical/m21/view.js` | Facade `createView(canvas)`: escolhe M1.2 (`../proto/view.js`) ou C (`view-c.js`) por `?troops=`; fallback para M1.2 se C falhar |
| `src/tactical/m21/view-c.js` | Renderer C com a mesma API de `createView` |
| `src/tactical/m21/arena.js` | Cena e sobreposições copiadas de `proto/view.js`: chão, bosques, rochas, relva, luz, câmara, preparação, anéis de alcance, setas, projécteis, partículas |
| `src/tactical/m21/troops.js` | Kits, esqueleto e pose adaptados de `src/tactical/visual/models.js`; sem HUD de demonstração |
| `src/tactical/m21/overlays.js` | Anéis, linhas de ordem, etiquetas 3D, alcances e camada de preparação, com a mesma geometria, cores e `renderOrder` de `view.js` |
| `src/tactical/m21/formations.js` | `slots()` do M1.2 para paridade; gramática C atrás de `?formations=c` |
| `tools/e2e-tactical-m21.mjs` | Harness de paridade, desempenho e capturas, com `tools/e2e-lib.mjs` |
| `docs/tactical/m2.1-validation-plan.md` | Este documento |

`proto/main.js` e `proto/view.js` **não são editados**. A cópia é intencional: o risco de deriva é
controlado pelo SHA no comentário e por um teste que compara o hash antes de cada execução.

### 2.2 Configuração

```
?troops=m1|c            # m1 por omissão no ensaio; c só por pedido explícito
&formations=m1|c        # m1 = mesmas posições; c = gramática nova (M2.1b)
&seed=1..20             # mesma semente que o protótipo
&stress=0|36|100|200    # coortes estáticas extra, sem simulação
&dist=110               # distância inicial da câmara
&autoplay=0|1           # arranca a batalha/preparação conforme o protocolo
```

- **M1.2 é o modo por omissão**, e o código de C só é importado dinamicamente quando `troops=c`; com
  `troops=m1` o pedido HTTP de `view-c.js` nem existe. É o kill switch, não uma bandeira cosmética.
- O selo do cabeçalho mostra `M1.2` ou `C` e, se houver fallback, `C → M1.2 (motivo)`.
- O botão **Restart as M1.2** recarrega a página com `troops=m1` e os mesmos `seed`, `dist` e formação.

### 2.3 O que C substitui

Só a camada dos soldados. O resto da cena e da interface é o mesmo objecto ou uma cópia fiel:

```
session.js ─► main.js ─► view.sync(groups, dt, opts)
                              ├─ soldados        M1.2 ou C
                              ├─ anéis/linhas    overlays.js (igual)
                              ├─ etiquetas/cartões  DOM de main.js (igual)
                              ├─ terreno/bosques arena.js (igual)
                              ├─ projécteis/pó   arena.js (igual)
                              └─ câmara/alcance  arena.js (igual)
```

O contrato de `createView` a respeitar, sem alterações de assinatura: `setPrep`, `setRanges`, `reset`,
`sync`, `volley`, `hit`, `charge`, `shake`, `where`, `pick`, `project`, `pan`, `zoom`, `rotate`,
`camera`, `render`, `info`. `info()` continua a devolver pelo menos `{ calls, triangles }`; C acrescenta
`geometries`, `textures` e `programs` sem quebrar o contrato.

## 3. Contrato de paridade

| Elemento | Regra de paridade |
| --- | --- |
| Semente e grupos | Mesma `seed`, mesmo `defaultPlacement`, mesmo `COLUMN_VARIANTS`, mesmo `session.js` |
| Câmara | `{ tx: 80, ty: 44, dist: 110, yaw: 0, pitch: 0.95 }`, limites `32–150`, FOV 38°, `pixelRatio ≤2` |
| Terreno e elevação | C usa `heightAt(x, y)` no pé de cada soldado; anéis e etiquetas projectados pelo mesmo código |
| Bosques, rochas, oclusão | Mesmos geradores e mesma ordem de desenho; a silhueta «raio-X» (`GreaterDepth`) mantém-se em C |
| Formações | `formations=m1`: o mesmo `slots(n, x, y, facing, marching)` e o mesmo `yaw` por homem. `formations=c`: só a disposição muda, nunca as posições lógicas dos grupos |
| Frente e combate | Mesmo `g.facing`, mesmo alvo em `g.engaged`, mesma regra de rodar para o alvo |
| Animação | Mapa de estados abaixo; o root de C fica no lugar do soldado, sem root motion |
| Acontecimentos | `volley`, `hit`, `charge`, `shake` e `onde` com os mesmos argumentos e tempos |
| Interface | Cópia de `main.js` e do HTML: cartões, etiquetas, linhas de ordem, selecção, resultados e relatório iguais |
| Mortos | Mesma lista, mesma queda, mesmos limites (`CAP` de vivos e de mortos) |
| Números | `view.info()` comparável; a simulação não lê nada da vista (garantido pela suíte) |

**Diferença permitida:** apenas o corpo, o equipamento, a pose e a cor dos soldados. Qualquer diferença
em anéis, terreno, etiquetas ou partículas é bug de paridade e bloqueia o passo.

### 3.1 Mapa de animação

| Estado/acontecimento M1.2 | Pose C |
| --- | --- |
| `order.type === 'mover'`, `pace === 'marcha'`, não engajado | Marcha, passo travado por grupo |
| `g.chargeT > 0` ou acontecimento `carga` | Carga: inclinação, passada longa, pó |
| `g.engaged` | Combate: guarda alta, golpe, pés fixos no lugar |
| `order.type === 'retirar'` e não engajado | Retirada: de costas, escudo para o inimigo |
| `g.state === 'debandada'` | Debandada: passo largo, direcções divergentes |
| `g.hidden` | Mesmo escurecimento 0,62 e silhueta «raio-X» |
| `s.flash` (baixas) | Mesmo flash vermelho; sem alterar a lógica de baixas |

### 3.2 Soldados e desempenho

A arena real tem **28 soldados** (15 lusitanos em 4 grupos; 13 romanos em 3 grupos). A paridade joga-se
sempre com esses 28. As medições de 36, 100 e 200 usam **coortes estáticas extra**: o mesmo roster,
repetido em filas fora da área de combate, sem simulação, sem ordens e sem baixas. Assim compara-se o
custo de desenhar N soldados sem alterar a batalha nem a IA. O valor 36 repete a referência do estudo
M2; 100 e 200 testam a escala de dezenas de grupos.

## 4. Protocolo de medição

### 4.1 Bancadas

1. **PC de referência**: GPU discreta, 1080p, Chrome estável, DPR 1, sombras ligadas.
2. **Portátil/browser**: GPU integrada, 1366×768, Chrome, DPR 1.
3. **Fallback de software** (apenas para detectar erros, nunca para metas de desempenho): SwiftShader.

Registar sempre `WEBGL_debug_renderer_info` (renderer e vendor), versão do Chrome, sistema e resolução.
Três execuções por configuração; aquecer 3 s e amostrar 5 s; reportar p50, p95 e máximo, nunca só a média.

### 4.2 O que medir

| Métrica | Como |
| --- | --- |
| Draw calls e triângulos | `view.info()` no fim de cada amostra; guardar também o total do `renderer.info` |
| Frame time | `requestAnimationFrame` no browser; p50/p95/máx; opcional `EXT_disjoint_timer_query_webgl2` para GPU |
| Memória | `performance.memory.usedJSHeapSize` (Chrome), `renderer.info.memory.geometries/textures`, contagem de objectos |
| Arranque | tempo até ao primeiro frame e bytes transferidos (CDP, como em `measure-tactical-proto.mjs`) |
| Erros | `pageerror` e `console.error`; falhas WebGL |
| Imagem | capturas a 110/65/40 m em preparação, espera, carga, combate e debandada |

Metas provisórias para C, a confirmar na primeira medição:

- 28 soldados: ≤ 45 draw calls de tropa.
- 200 soldados: ≤ 60 draw calls, ≤ 150 mil triângulos, p95 ≤ 16,7 ms no PC de referência e ≤ 25 ms no
  portátil/browser.
- Memória adicional face a M1.2: ≤ 40 MB.
- M1.2 inalterado: 5 draw calls de tropa e ~8,7 mil triângulos para os 28–36 soldados do ensaio.

### 4.3 Paridade

- Seis estratégias dos robôs existentes (`tools/tactical-bots.mjs`) × sementes 1–20, com M1.2 e C:
  comparar o relatório JSON (desfecho, baixas, tempos, momentos-chave, flancos) **sem** os campos de
  renderer. 120 de 120 têm de coincidir.
- Repetir uma batalha com renderer C e com a vista M1.2 a 60 fps e a 20 fps: o passo fixo da simulação
  não pode mudar o resultado.
- Verificar `pick()` em cinco pontos do ecrã (cada grupo e um ponto vazio) e `project()` das etiquetas
  com tolerância de 1 px.

### 4.4 Teste cego

Cinco participantes, dez pares de imagens (M1.2 à esquerda ou à direita, ordem aleatória), sem
etiquetas de facção:

1. «Qual dos lados é Roma? Qual é a Lusitânia?» (acerto e tempo).
2. «Em que estado está cada grupo?» (marcha, carga, combate, retirada, debandada).
3. «Qual dos dois se lê melhor como tropa?» (preferência, sem justificar).

Critério: ≥ 80% de acerto de facção e estado em C; preferência ≥ 4/5. As respostas e os tempos ficam em
`production/qa/evidence/tactical-m21/blind/`.

## 8. Riscos e mitigação

| Risco | Mitigação |
| --- | --- |
| Cópia de `main.js` deriva do original | SHA-256 comentado + teste; só o import e o bloco de config diferem |
| Sobreposições (anéis, linhas, etiquetas) divergem | `overlays.js` copiado linha a linha + diff de imagem; qualquer diferença bloqueia |
| Oclusão/«raio-X» diferente | Mesmo `depthFunc`, mesma regra por grupo; silhueta fantasma fundida por papel (4 chamadas, não 38) |
| Elevação diferente | `heightAt` no pé, anéis e projecções iguais; teste em colina e ribeiro |
| Paleta muda com a luz/fog da arena | Comparar capturas na arena real, não na demonstração; ajustar só os materiais das tropas |
| Stress não representa uma batalha | Medir sempre também os 28 nativos; stress só para isolar custo de desenho |
| Hardware variável | 2 bancadas + string da GPU; metas separadas PC/browser; software excluído |
| Custo de C no browser | LOD1 (corpo fundido de A) acima de 90 m, LOD2 acima de 150 m; fallback `troops=a` |
| Deriva para a simulação | Guarda de diff em `sim.js`, `combat.js`, `data.js`, `roman-stub.js`, `session.js`, `field.js` e campanha |

## 9. Componentes de A como alternativa de baixo custo

A não é só um plano B: quatro dos seus elementos são melhorias independentes e podem entrar antes de C.

| Componente de A | Onde está | Ganho | Custo |
| --- | --- | --- | --- |
| Escudos maiores e inclinados 20–25° para cima | `simpleBody` em `src/tactical/visual/models.js` | **O maior ganho de leitura por linha de código**: o escudo passa de 1–2 px a uma oval legível | 1–2 dias no `view.js` actual |
| Bloco de cor por facção + crista + pano no ombro | idem | Separação imediata a 65–110 m | 1 dia |
| Silhuetas de papel fundidas: oval/redondo, orelhas de lobo, cajado de funda | idem | Papéis distinguem-se sem articulação | 1–2 dias |
| Signum e pelt do signífero | idem | Âncora de facção e de posição da formação | 1 dia |
| Formação com filas, intervalos e lugares por papel | `slots`/`formations` | Orientação e frente legíveis sem geometria nova | 1–2 dias |
| Balanço/inclinação/Investida de corpo inteiro | `motionOf` | Marcha e carga mais vivas, sem esqueleto | 0,5 dia |
| **A como LOD1 de C** | `simpleKit` | Acima de ~90 m, corpo fundido com a mesma paleta: ~4 draw calls e ~35% dos triângulos | 1–2 dias, já previsto em M2.5 |
| **A como fallback de GPU** | `troops=a` | Se C falhar as metas no browser/iGPU, mantém a identidade sem o custo de B | 0,5 dia no facade |

O que A **não** resolve: passada articulada, guarda e golpe em combate, equipamento fino a 28 m e a
leitura de impacto. É uma ponte e um LOD, não o destino. Recomendação: mesmo com C aprovado, aplicar a
inclinação dos escudos, a paleta, a crista e o signum ao M1.2 como melhoria imediata (2–4 dias), e
reservar A como LOD1/fallback de C.

## 10. O que fica fora

Sem alterações a `sim.js`, `combat.js`, `data.js`, `roman-stub.js`, `session.js`, `field.js`, à campanha,
ao mapa estratégico, às gravações, ao `index.html` e ao protótipo jogável. Sem assets novos, sem shaders
personalizados, sem merge. A integração só acontece com nova aprovação depois do relatório de M2.1.
